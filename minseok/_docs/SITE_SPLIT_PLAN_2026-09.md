## 아키텍처 원칙 (변경 없음 — 명문화)

- 백엔드는 **헥사고날/클린 + DDD/SOLID + 스타 토폴로지(허브-스포크)** 유지. market·stock은
  이미 상호 독립 스포크(import-linter 5계약 강제)이고, 이 계획의 어떤 단계도 이 구조를 바꾸지
  않는다 — 사이트 분리는 **표면(프론트·도메인·브랜드)의 분리**이지 백엔드 분리가 아니다.
- LLM 추론은 계속 `core/llm/llm_orchestrator.py` 단일 수렴(단일 모델 정책).
- 개발 비용 0원 원칙 유지. 유일한 신규 비용은 도메인 등록비(연 1~2만원/개) — 사용자 결제 결정.

## 판단: 지금부터 준비하는 게 좋은가? → **이음새만 지금, 분리는 나중에**

**지금 사이트를 쪼개지 않는다.** 대신 나중의 분리가 값싸지도록 **이음새(seam)를 지금 만든다.**

근거:
1. **백엔드는 이미 준비돼 있다.** market↔stock 직접 참조 0(계약으로 강제), market 전용 DB
   분리(:5434), 교차 협력은 허브 경유뿐. 도메인이 갈라져도 백엔드는 지금 모놀리스 그대로
   `api.redoceanmap.com` 하나로 양쪽을 서빙하면 된다. 1인 운영에서 백엔드 분리 배포는
   관측·배포·백업 부담이 2배가 되므로 **명시적 비추천**(과설계 목록 후보).
2. **갈라야 하는 것은 프론트 표면이다.** www 하나에 주식·상권·챗이 한 AppShell로 묶여 있고
   브랜드 토큰이 단일이다. 이건 지금부터 값싸게 준비 가능하다(아래 Phase A).
3. **규제가 분리를 지지한다.** 유사투자자문업 신고([[ROADMAP]] [0-2])는 **주식 쪽만의**
   공개 게이트다. 도메인을 나누면 상권 사이트는 신고와 무관하게 먼저 공개할 수 있다 —
   분리의 가장 실질적인 이득. (EXAONE NC 라이선스 해소는 양쪽 공통 선행.)
4. **역방향 근거**: 지금 두 저장소/두 앱으로 쪼개면 auth·chat·디자인 시스템·검증 파이프가
   전부 이중화된다. 트래픽 0 단계에서 이중화는 순비용이다.

## 벤치마크 ① — 재개발닷컴(jaegebal.com) 분석 → 상권 사이트 이식

**정체**: 재개발·재건축 수직 특화 데이터 플랫폼("재개발 실거래는 재개발닷컴"). 웹+앱.
구역(zone)별 실거래가·사업 진행현황·조합원 매물·경매 + 고시/공고 자동 수집(시간 단위) +
구역별 커뮤니티 + 뉴스/블로그 큐레이션 + AI 감정 순위. 수익은 광고(광고 문의 메뉴).

**성공 문법 (우리 상권 사이트에 이식할 것)**:

| 재개발닷컴 문법 | 우리 대응물 | 상태 |
|---|---|---|
| **구역 = 앵커 단위** (모든 정보가 구역 페이지로 수렴) | 상권(trdar) 상세 — `/areas` 랭킹 + 점수/분해 | 있음(로그인 뒤) → **공개 상세 페이지로 승격 필요** |
| 구역별 페이지가 SEO 유입 라우트 | 상권 1,650개 × 업종 상세 = 롱테일 검색 유입 | 없음 — Phase A-4 |
| 공식 데이터 자동 갱신 피드(고시·공고) | 분기 팩트 자동적재(③-M5)·인허가 cron·상권 뉴스 cron | 있음(백엔드) → 화면 피드로 노출 |
| 관심 구역 새 매물 **알림** | 북마크 상권 알림(B1)·뉴스 알림(B9 파이프 공유) | 부품 보유, 미조립 |
| AI 감정 순위(내 물건 평가) | 종합점수·업종 랭킹·"내 가게 진단"(B3) | 점수는 있음, B3은 Phase 6 |
| 커뮤니티(구역 게시판) | — | **기각 유지**(ROADMAP: 모더레이션 상근·리딩방화·콜드스타트) |
| 매물/경매(거래 축) | — | **비이식**: 중개 알선은 공인중개사법 영역(기존 기각과 동일 근거) |

**핵심 시사점**: 재개발닷컴의 해자는 "공공정보를 구역 관점으로 재구조화 + 자동 갱신 + 알림"이다.
우리는 데이터·cron·점수를 이미 갖고 있고, **없는 것은 공개 SEO 표면과 알림 조립**이다.
채팅 중심 UI는 검색 유입이 0이다 — 상권 사이트의 성장 루프는 상세 페이지가 만든다.

### 확정 방향 (2026-09-01 사용자 결정): 데이터 표면이 본진, 챗은 그 위의 코파일럿

재개발닷컴형 구역(상권) 페이지를 본진으로 깔고 **그 위에 우리 챗을 얹는다** — 재개발닷컴이
구역 페이지 위에 커뮤니티(사람들의 해석)를 얹은 자리에, 우리는 AI 분석 대화를 얹는다
(커뮤니티 기각 판단 유지). 이 역전이 기존 챗의 구조적 문제를 해소한다:

1. **상권 특정 실패(422류) 소멸**: 상세 페이지에서 연 챗은 그 페이지의 trdar_code가 곧
   컨텍스트 — phase1(후보 선택, 오답·지연의 주원인)을 건너뛰고 phase2만 돈다.
   → 백엔드 슬라이스: `AskRequest.areaCode`(선택) 수용 + phase1 생략 경로
   (지시어 가드·직전 추천 승계와 같은 결의 결정론 시딩).
2. **카드-본문 모순 축소**: 챗이 사용자가 보고 있는 화면의 숫자를 근거로 말하게 된다.
   챗의 역할은 서술이 아니라 해석("이 수치가 나한테 무슨 뜻이냐") — 테스트에서 잘한 축.
3. **홈 문법 역전**: 상권 사이트 홈 = 랭킹·지도·갱신 피드(챗 입력창은 주인공이 아님),
   챗은 상세 페이지의 도크. A-4와 같은 작업 묶음.
4. **공개 순서**: 페이지(비LLM)는 라이선스 게이트와 무관하게 먼저 공개 가능 —
   챗 도크는 LLM 교체(③-M5②) 뒤에 켠다. 게이트가 사이트 공개를 막지 않게 된다.

### 확장 후보 — 주거·부동산 축 (2026-09-01 사용자 의향: 아파트·빌라·오피스텔·재개발/부동산 뉴스)

**포지셔닝**: 재개발닷컴의 본진(재개발 수직 — 고시 파싱·조합원 매물)과 정면 승부하지 않는다.
우리 자리는 **"동네(행정동) 데이터 플랫폼"** — 한 지역 페이지에 상권(창업)·주거 시세·지역
뉴스를 함께 놓고 챗이 해석한다. 행정동 롤업(I-3)이 이미 상권-주거 통합 앵커다.
재개발은 그 동네의 이벤트 축(정비구역 여부·관련 뉴스)으로만 다룬다.

비용 순서(전부 무료 API — DATA_GO_KR 키 보유):
1. **뉴스 축**: 상권 뉴스 cron에 부동산·재개발 키워드/RSS 추가 — 수집→bge-m3 임베딩→챗 근거
   카드 파이프 그대로(며칠 규모).
2. **주거 실거래**: `collect_commercial_trades.py`(국토부 상업업무용, 자치구×월) 복제로
   아파트·연립다세대(빌라)·오피스텔 매매+전월세 수집 → 행정동 집계 → 지역 페이지 시세 블록
   (1~2주 규모, dry-run 게이트·독립 마이그레이션 등 기존 수집 규칙 그대로).
3. **재개발 축**(정비구역·고시 요약): 신규 파싱 표면 — ①②의 트래픽 신호 뒤(수요 게이트).

챗 편입은 페이지 컨텍스트 주입(위 areaCode → 행정동 일반화)으로 자연 해결 — 시세·뉴스
블록이 컨텍스트에 실리면 된다. **phase0 부동산 의도 신설은 데이터 축적 뒤**(재료가 구조보다
먼저). 기각 유지: 매물/호가·경매(중개 영역)·커뮤니티.

**데이터 갭 진단(2026-09-01)** — 부족분은 전부 무료 공공데이터로 충당 가능:
- 신규 수집 필요: 국토부 주거 실거래 6종(아파트·연립다세대·오피스텔 × 매매/전월세) —
  기존 `collect_commercial_trades.py` 패밀리·같은 DATA_GO_KR 키.
- ⚠ **법정동↔행정동 매핑 선행**: 실거래는 법정동, 우리 지역 축은 행정동 — 행안부 행정구역
  코드 매핑(정적) 1회 적재 없이는 시세 블록이 지역 페이지에 못 붙는다.
- 단지 페이지·지도 핀은 K-apt 단지정보 + 지오코딩(카카오 무료 쿼터)이 추가 필요 —
  ①차는 행정동 집계로 시작해 이 둘을 미룬다(수요 게이트 뒤).
- 여전히 없는 것: 상가 임대료(R-ONE 키 = 사용자, B4). 공시가·경매는 포지셔닝상 불채택.

## 실행 계획

### Phase A — 지금 (코드 이음새, 비용 0, 각 항목 독립)

1. **A-1 도메인 라우팅 이음새**: Next `middleware.ts`에 host 기반 분기 골격
   (`stock.example` → `/stock` 트리, `market.example` → `/areas` 트리). 도메인이 없어도
   `?site=` 쿼리/서브도메인으로 검증 가능. AppShell 내비를 site 스코프 파라미터로.
2. **A-2 브랜드 토큰 이원화 준비**: `globals.css` 토큰을 `[data-site="stock"|"market"]`
   오버라이드 구조로. DESIGN.md에 "두 브랜드" 절 신설(주식=토스 결, 상권=데이터 플랫폼 결).
   기본값은 현행 토큰 — 기존 화면 무손상.
3. **A-3 auth 쿠키 전략 결정**(코드보다 결정이 먼저): 새 도메인은 `.redoceanmap.com` 쿠키가
   안 붙는다. 선택지 — (a) 사이트별 독립 로그인(단순, 권장 초기값) (b) auth 오리진 공유 SSO
   (redirect 왕복, ③-M1 이중문 구조 재사용). **결정 전까지 auth 코드 무변경.**
4. ~~**A-4 상권 공개 상세 = SEO 앵커**~~ — **완료(2026-09-14, mac)**. 백엔드 `area_public`
   슬라이스(`GET /market/areas/{code}/public` 60/분 · `/market/areas/public-index` 10/분,
   `core/rate_limit` 재사용, 하루 캐시) — 상세·점수 유스케이스 조합만, 공개 필드는 `AreaPublicView`가
   명시(사용자 결정: 핵심 요약+해석 문장, 좌표·인허가 상호·인구 피라미드·업종 랭킹 표 제외).
   프론트 `www/app/areas/[trdarCode]/page.tsx`(`(seoul)` 밖 서버 컴포넌트, ISR 하루,
   `generateMetadata`) + `app/sitemap.ts`(1,650건) + `app/robots.ts`. 서버 fetch는
   `lib/publicApi.server.ts`(브라우저 절대 URL 금지 규칙의 서버 측 예외 — 파일 주석). 챗 도크는
   LLM 교체 뒤. `tests/test_public_routes.py`가 공개 집합 3경로 + rate limit 부착을 고정.
5. **A-5 이름 후보 정리(사용자)**: 도메인 2개 후보. 백엔드 API는 `api.redoceanmap.com` 유지.

### Phase B — 도메인 구매 시 (반나절 규모)

6. Vercel 프로젝트에 도메인 2개 추가 → A-1 미들웨어에 실호스트 연결.
7. 도메인별 홈 분리: 상권 홈=랭킹/지도/피드 중심, 주식 홈=관심 종목 보드 중심.

### Phase C — 공개·성장 게이트 뒤 (수요가 생겼을 때만)

9. 상권 사이트 선공개(신고 불요) → 주식은 유사투자자문업 신고 + LLM 교체(③-M5②) 뒤.

    백엔드 분리 배포는 계속 비추천.

### 순서 제약

- Phase A는 서비스 품질 Phase 0~3(진행 중)과 독립 — 끼어들 필요 없음. 현 스프린트 종료 후 착수.
- A-4(공개 상세)는 rate limit 선행. A-2는 DESIGN.md 갱신이 코드보다 먼저.
- 챗은 양 사이트 공용 부품으로 남긴다 — phase0 의도 분류가 이미 도메인 게이트라,
  사이트별로 허용 의도만 제한하면 된다(주식 사이트 챗 = stock·market_news만).
