## 1. 어느 게임을 먼저 하는가 — 판정: 모의투자

| 기준 | 모의투자 | 상권 창업 |
|---|---|---|
| 외부 의존 | **0** — game 도메인 + 자기 테이블만 | 허브 신규 포트 + market 게이트웨이 + `main.py` 배선 = **3앱 동시 변경** |
| 프론트 | 표·차트(`CandleChart` 기존 패턴 재사용) | 지도 + 진단 패널 + 시뮬 결과 3영역 |
| 단독 롤백 | 쉽다(패키지 삭제 + `main.py` 2줄) | 3앱 되돌림 |
| 공통 토대 | **시계·시드·지갑·원장을 여기서 먼저 실증한다** | 이 토대를 전제로 한다 |
| 프로젝트 핵심 가치 | 보통 | **높다**(상권 실데이터 활용) |

**판정: 투자 먼저.** 상권을 먼저 하면 시계·지갑·원장을 상권 게임 안에 짜 넣게 되고, 나중에
투자가 붙을 때 전부 재작업이다.

다만 **핵심 가치를 늦추는 대가를 최소화하기 위해 투자 게임의 범위를 극단적으로 자른다** —
1단계는 가격 곡선 조회뿐, 3단계에 롱/숏 1종 + 지갑, **이벤트는 상권 게임 뒤(9단계)로 미룬다.**

## 2. 단계 요약 — 각 단계는 단독 배포·단독 롤백 가능

| 단계 | 내용 | 슬라이스 | 새 테이블 | 새 허브 포트 | 커밋 |
|---|---|---|---|---|---|
| **0** | ROADMAP 스포크 판정 + 하네스 게이트 6개 답 (**코드 0줄**) | 0 | 0 | 0 | `docs(game): 스포크 판정과 도입 게이트` |
| **1** | 앱 골격 + 결정론 시계 + 가상 시세 엔진 | **2**<br>`rulebook`·`market_price` | **0** | 0 | `feat(game): 결정론 시계와 가상 시세 엔진` |
| **2** | **프론트 시세 화면** — `/game` 신규 라우트 + 상단 게임 탭 신설(전 유저 공개 · `TAB_KEYS` 미편입, harness §10-1). 읽기 전용 차트, 폴링 30초 | 0 | 0 | 0 | `feat(www): 게임 시세 화면` |
| **3** | 지갑 · 롱/숏 · 원장 | **2**<br>`wallet`·`trade` | 3 | 0 | 마이그레이션 / 슬라이스 **2커밋** |
| **4** | **프론트 매매 UI** — 2단계 화면에 주문·포지션·손익 추가 | 0 | 0 | 0 | `feat(www): 모의투자 매매` |
| **5** | 허브 `AreaDemandProfilePort` + market 게이트웨이 + **적합도 미리보기(소비자)** | **1**<br>`area_fitness` | 0 | **1** | **1커밋**(게이트 ③) |
| **6** | 창업 · 일일 시뮬레이션 | **2**<br>`store_open`·`store_daily` | 2 | 0 | 마이그레이션 / 슬라이스 **2커밋** |
| **7** | **프론트 상권 화면** — `MapView` 핀 선택 + 적합도 진단 + 일일 매출 | 0 | 0 | 0 | `feat(www): 상권 창업 화면` |
| **8** | 분기 결산(지연 실행) **+ 결산 화면** | **1**<br>`settlement` | 1 | 0 | 마이그레이션 / 슬라이스+화면 **2커밋** |
| **9** | 시장 이벤트 + 밸런스 실측 리포트 | 0 | 0 | 0 | `feat(game): 호재·악재 이벤트` / `docs(game): 밸런스 실측` |

> **⚠️ 이 표는 0단계에서 한 번 재배치됐다.** 게이트 ④("화면 없이 슬라이스 4개 이상 금지")를
> 검증하다 **원래 표가 스스로를 위반**하고 있음을 발견했다 — 구 1단계(2) + 구 2단계(2)로
> 화면 없이 4개가 쌓이고 있었다. 프론트를 두 번(2·4단계)으로 쪼개 해소했다.
> 연속 슬라이스 수는 이제 전 구간 3개 이하다(harness §6-④ 표).

> **프론트를 2단계로 앞당긴 것은 게이트 때문만이 아니다.** 1단계에서 만든 결정론 시세 엔진이
> **그럴듯한 곡선을 그리는지 눈으로 먼저 확인**하고 나서 매매를 얹는 편이 맞다. 차트가 계단이나
> 직선으로 나오면 그건 브리지 구현 버그이고, 매매 로직을 얹기 전에 잡아야 한다.

> **9단계(이벤트)를 왜 마지막에 두나:** 이벤트는 재미의 핵심이지만 **밸런스 파괴력이 가장 크다.**
> 두 게임의 기준 수익률 분포를 먼저 실측하지 않고 이벤트를 얹으면, 결과가 이상해졌을 때
> 원인이 모델인지 이벤트인지 가릴 수 없다.

## 3. 게임 1 — 모의투자 시스템 설계

### 3-1. 가상 주가 모델

**모델: 로그정규 랜덤워크 + 이벤트 점프.** 스토캐스틱 변동성·GARCH는 체감 차이가 없어 쓰지 않는다.
구현 형태는 game-harness §1-2의 2단 브라운 브리지다.

**종목 수: 12~16.** 68 전부는 화면이 감당 못 하고 밸런스 조정도 불가능하다.
σ 분위수 균등 샘플(저변동 4 · 중 6 · 고 4) + 섹터 중복 제거. `SPY`·`^VIX`는 지수라 제외.

**종목명은 가상 사명 + 실제 업종**(결정 7). 예: `한빛전자(반도체)` · `대동모빌리티(전기차)` ·
`서진바이오(제약)`. 실 티커 매핑은 캘리브레이션 스크립트 안에서 익명화하고 결과 상수에는 남기지
않는다 — 섹터 이벤트("반도체 업황 회복")의 서사는 그대로 살아있다.

**캘리브레이션** — `scripts/calibrate_game_symbols.py` → `game/domain/market/symbol_params.py`

| 파라미터 | 산출 | 처리 | 근거 |
|---|---|---|---|
| `sigma_daily` | `price_bars(1d)` 로그수익 표준편차 | **[0.008, 0.060] 클리핑** | 이상치 종목(GME 등)이 게임을 지배하지 않게 |
| `mu_daily` | 로그수익 평균 | 클리핑 후 **전 종목 평균 0으로 중심화** | ⚠️ **실드리프트를 그대로 쓰면 안 된다.** 미국 대형주가 무조건 우상향해 최적 전략이 "고μ 종목 매수 후 방치"로 고정된다 — 그러면 게임이 아니다 |
| `sigma_game` | `sigma_daily × K`, **K = 1.5** | 계수 파일 | 현실 1시간(게임 1일)만 봐도 하루치 변동이 지나가야 체감이 산다 |
| `sector` | 워치리스트 분류 | — | 섹터 이벤트의 영향 범위 |

### 3-2. 롱/숏 규칙

| 항목 | 결정 | 근거 |
|---|---|---|
| 레버리지 | **없다(1배).** 숏은 증거금 100% | ⚠️ **청산 로직은 오프라인 진행과 최악의 궁합이다.** 미접속 중 청산되면 "게임오버 없음" 원칙과 충돌하고, 청산 시점을 결정론으로 확정하려면 경과 틱을 전량 순회해야 해서 §1-2의 O(log) 설계가 무너진다 |
| 숏 손실 상한 | **증거금까지.** 지갑은 음수가 되지 않는다(불변식) | 숏 무한손실 차단 |
| 수수료 | 체결당 **0.15%**(왕복 0.3%) + 숏 보유비용 게임 1일당 **0.02%** | 무수수료면 최적 전략이 매 틱 스캘핑이 된다 — 우리가 없애려던 탭 노가다의 재발명 |
| 체결가 | **요청이 도착한 틱의 가격.** 지연 체결 없음 | 미래 틱 조회 차단(harness §1-6)과 짝 — "다음 틱에 체결"이라는 개념 자체가 성립하지 않는다 |

> **잔고 하한을 "보전"이 아니라 "예약"으로 구현한 이유(3단계).**
> 원안은 *"잔고가 10만원 아래로 내려가면 손실을 적용하지 않는다"*였는데, 그건 **게임이 돈을
> 만들어내는 것**이라 원장 불변식(§6-3)이 깨진다. 대신 **투자 가능액 = 잔고 − 10만원**으로
> 두면, 손실 상한이 투입액이므로 잔고가 하한 아래로 내려갈 수 **없고** 원장은 현금 흐름과
> 정확히 일치한 채로 남는다. 결과는 같고 회계는 깨지지 않는다.
| 잔고 하한 | **10만원을 투자에 쓸 수 없게 예약한다** | 파산 없음(아이러브커피 ③). ⚠️ 3단계에서 "손실을 깎아 보전"에서 바꿨다 — 아래 참고 |

### 3-3. 이벤트 스펙 (9단계)

**슬롯:** 게임 6시간(15틱)마다 1슬롯 = 게임 하루 4슬롯. 슬롯당 발생 확률 **p = 0.25**
→ 평균 게임 1일 1건 = **현실 1시간에 1건**.

| 유형 | 비중 | 영향 범위 | 즉시 충격 | 지속 드리프트 | 지속 |
|---|---|---|---|---|---|
| 종목 호재/악재 | 70% | 1종목 | ±1.5~6.0% | ±0.30%/게임일 | 게임 3일 |
| 섹터 | 20% | 섹터 3~5종목 | ±1.0~3.0% | ±0.20%/게임일 | 게임 5일 |
| 시장 전체 | 10% | 전 종목 | ±2.0~5.0% | ±0.40%/게임일 | 게임 2일 |

- 즉시 충격은 **3틱에 걸쳐 선형 반영**한다(차트가 수직선이 되지 않게).
- 지속분은 지수감쇠 `exp(-Δ/τ)`.
- 문구는 **템플릿 룩업**(유형×부호별 8문장), 인덱스는 `H(EPOCH, "event", slot)`.
  **LLM 미사용** — 결정론 위반이고 추론 비용이 든다.
- 이벤트도 결정론이다. 유저는 "방금 뜬 뉴스"로 보지만 서버는 과거 어느 슬롯이든 같은 목록을
  재현한다 — 그래서 이벤트 로그 테이블이 필요 없다.

### 3-4. 밸런스 계약 — 이 표가 유일한 조정 근거다

난이도 "현실적"(결정 9) 기준. 1게임분기 = 90게임일 = 현실 3.75일.

| 지표 | 목표 |
|---|---|
| 중앙값 | **+5 ~ +15%** |
| 상위 10% | +50% 내외 |
| 하위 10% | **-30% 내외** (하한 10만원) |
| 손실 계정 비율 | **35~45%** |

검증: `scripts/simulate_game_balance.py`가 무작위 전략 1,000회 × 90게임일 시뮬 → 분위수 표.
**계수 조정은 이 표를 근거로만 한다** — 감으로 고치지 않는다.

## 4. 게임 2 — 상권 창업 시스템 설계

### 4-1. 매출 산식 — 실데이터에서 유도한다

```
기대_점포당_월매출 = observed_monthly_sales_amount / max(observed_store_count, 1)
기대_객단가        = observed_monthly_sales_amount / max(observed_monthly_sales_count, 1)
```

> ⚠️ **집계 축 함정.** `estimated_sales.monthly_sales_amount`는 (분기, 상권, **업종**) 축의
> 행이고 `store.store_count`도 같은 축의 행이다. `similar_industry_store_count`와 섞지 않는다.
> market이 이미 겪은 함정이다 — 성별 괴리를 전 업종 합산으로 재는 바람에 임계값 0.15가
> 48%에서 발화했다. **축 일치 회귀 테스트를 쓴다.**

```
simulated_daily_sales(d)
  = 기대_점포당_월매출 / 30
  × awareness(d)          # 1 - exp(-d/30), 하한 0.15 — 신규 창업 페널티
  × fitness               # 0.4 ~ 1.6  — 적합도(§4-2)
  × price_factor          # 0.6 ~ 1.3  — 가격 정책(객단가↑ 건수↓)
  × capacity_factor       # 시설·직원(§4-4) — 매출 상한 역할
  × competition_factor    # 유사업종 점포수 기반
  × weekday_factor(d%7)   # 실데이터 요일 비중 ÷ (1/7)
  × noise                 # H(EPOCH, store, d) → ±12%
```

### 4-2. 적합도 — "이상한 곳에 이상한 업종"의 핵심

| 축 | 산출 | 실데이터 출처 | 가중치 |
|---|---|---|---|
| ① 수요 정합 | 업종의 서울 전체 매출 **연령·성별 분포** ↔ 그 상권 유동/상주 **연령·성별 분포**의 코사인 유사도 | `estimated_sales` age/gender × `floating`/`resident_population` | 0.35 |
| ② 시간대 정합 | 업종의 시간대 **매출 비중** ↔ 상권의 시간대 **유동인구 비중** 코사인 | `estimated_sales` time_* × `floating_population` time_* | 0.30 |
| ③ 포화도 | `similar_industry_store_count / 유동인구`의 **서울 백분위**(높을수록 감점) | `store` × `floating_population` | 0.20 |
| ④ 생존 신호 | 그 상권·업종의 `closure_rate`·`operating_months_avg` 서울 백분위 | `store` · `commercial_change` | 0.15 |

`fitness = 0.4 + 1.2 × Σ(wᵢ · scoreᵢ)` — 가중치는 `rule_coefficients.py`.

> ⚠️ **임계값은 전부 서울 실측 분위수에서 잡는다.** 상식적인 값을 쓰면 아무것도 안 뜨거나
> 절반이 뜬다 — market이 시설 임계값에서 이미 겪었다(중앙 0 · p90 1인데 "5곳 이상"으로 잡아
> 전 서울에서 2상권만 발화). **분위수를 먼저 재고 나서 임계값을 정한다.**

### 4-3. 손님 NPC 생성 — 상권 데이터에서 형성한다

하루 방문 건수: `N(d) = simulated_daily_sales(d) / 기대_객단가`.

**N명의 객체를 만들지 않는다.** 화면 표시용 **표본 K = 40명**만 생성하고 나머지는 집계로 둔다
(1,000명 객체 생성은 응답 지연이고 화면에 보이지도 않는다).

표본 1명 = **(요일, 시간대, 성별, 연령) 4축**. 각 축을 실데이터 비중의 누적분포로 만들고
`H(EPOCH, store, d, i)`를 `[0,1)`로 바꿔 **역변환 샘플링**한다.

> ⚠️ **교차 분포가 데이터에 없다.** 매출 테이블에는 성별×연령 교차가 없고(`resident`·`working`
> 인구에만 있다) → **축 독립 가정**을 쓴다. 이건 가정치이므로 `assumed` 표기 대상이고
> UI에도 명시한다(harness §5).

**손님 취향 — 아이러브커피 ② 이식.** 손님마다 결정론 취향 태그를 붙인다
(아침 테이크아웃 / 장시간 체류 / 단체 / 가성비). 가게 설정(영업시간·좌석·메뉴·가격)과 맞으면
만족도가 오르고 다음 날 `awareness`에 `+α`가 붙는다.

> **탭 노가다 없이 ②를 옮기는 방법이 이것이다.** 유저는 개별 손님을 접대하지 않는다 —
> **손님 분포에 가게 설정을 맞춘다.** 원작이 "이 손님이 원하는 커피를 만들어라"였다면
> 우리는 "이 상권에 오는 손님들이 원하는 가게를 만들어라"다.

### 4-4. 성장 축 — 꾸미기 점수의 대체물 (아이러브커피 ① 이식)

| 장치 | 원작 | 우리 구현 |
|---|---|---|
| 동시 수용 | 꾸미기 10점당 손님 +1명 | `facility_score` **10점당 좌석 +1** → 일 최대 건수 = 좌석 × 회전율 × 영업시간 = **매출 상한(cap)** |
| 최속 임계값 | 850점 | `facility_score ≥ 850`에서 **회전율 계수 최대(1.0)** 도달, 그 이상은 수용인원만 증가 |
| 확장 선행조건 | 꾸미기 점수 | 2호점 = `facility_score ≥ 300` **+ 흑자 2분기 연속** |

> **왜 이 장치가 좋은가:** 매출 상한이 시설점수로 결정되면 **"좋은 상권 + 낮은 시설"은 손님을
> 돌려보낸다.** "상권은 좋은데 내 가게가 못 받는다"가 숫자로 보인다 — 이게 우리 게임의 ①이다.

다른 성장 축: 직원(회전율·만족도) · 메뉴(객단가·원가율) · 마케팅(`awareness` 가속).

### 4-5. 비용 산식 — 게임 규칙이되 실데이터에 앵커를 건다

**임대료·인건비·원가 데이터가 없다**(harness §0). 아래는 전부 `assumed_*`이며 UI에 가정치 배지가 붙는다.

| 항목 | 산식 | 앵커 근거 | 계수 |
|---|---|---|---|
| `assumed_monthly_rent_krw` | `기대_점포당_월매출 × RENT_RATIO × 입지계수` | 입지계수 = 그 상권 유동인구의 서울 백분위 → 0.6~1.6 | `RENT_RATIO = 0.10` |
| `assumed_labor_cost_krw` | `직원수 × BASE_WAGE` | 최저임금 월환산 근사 | `BASE_WAGE = 2_300_000` |
| `assumed_cogs_krw` | `매출 × COGS_RATIO(업종 대분류)` | 카페 0.35 / 음식 0.40 / 소매 0.60 | 업종 대분류 표 |
| `assumed_utility_krw` | `매출 × 0.03 + 300_000` | — | — |
| 초기 창업비 | `보증금 = 임대료 × 10` + `인테리어 = 면적 × 단가` | **보증금은 폐업 시 회수 가능** | — |

**계수 교체 구조:** 각 값은 `Coefficient(값, source="rule")`. 실데이터가 생기면
`source="observed"`로 바꾸는 것만으로 가정치 배지가 사라진다(harness §5-3).

### 4-6. 실패 판정 — 어떤 숫자가 어떻게 나빠지는가

난이도 "현실적"(결정 9): **무작위 입지·업종 선택의 중앙값은 소폭 적자**, 잘 고르면 분기당 +10~20%.

| 신호 | 나쁠 때의 수치 | 화면 문구(템플릿) |
|---|---|---|
| 적합도 0.4~0.6 | 일매출이 상권 평균 점포의 **40%** | "이 상권 유동인구의 절반이 50대인데, 이 업종 매출의 62%는 20대에서 나옵니다" |
| 시간대 미스매치 | 영업시간의 **70%에 손님 0** | "17-21시에 이 상권 유동인구의 8%만 지나갑니다" |
| 포화 | 유사업종 점포수 서울 상위 5% | "같은 업종 32곳 — 서울 상위 3%입니다" |
| 생존 | 그 조합의 폐업률 서울 상위 10% | "이 상권·업종 조합의 실제 폐업률은 서울 평균의 2.1배입니다" |
| 수용 한계 | 좌석 만석 시간 비율 > 60% | "손님의 24%가 자리가 없어 돌아갔습니다" |

**파산은 없다.** 잔고 부족 시 폐업이 아니라 **휴업**(매출 0, 임대료만 발생)이고, 자발적 폐업 시
보증금을 회수한다. 게임오버 화면을 만들지 않는다.

### 4-7. 분기 결산

- 게임 90일마다 `game_quarter_settlements` 1행.
- **지연 실행** — 유저 요청이 올 때 밀린 분기를 순서대로 확정한다(**cron 0개**).
- 누적 계산은 `settled_through_day` 앵커 이후만 → **최대 90일 순회**.
  이게 앵커의 정당한 자리다. 분기 결산은 캐시가 아니라 **게임 규칙상 실재하는 사건**이므로
  저장이 맞다(harness §4-2).
- 내용: 총매출 · 비용 4분해 · 순익 · 적합도 진단 · **서울 동일업종 실데이터 대비 백분위** ·
  다음 분기 조언 3줄.

## 6. 지갑 공유 구조와 밸런스 위험

**구조:** `game_wallets(user_id UNIQUE, cash_krw, epoch_id, rule_version)` 1행.
투자↔창업 자본 이동에 제한을 두지 않는다.

**위험:** 한쪽의 기대수익이 다른 쪽을 압도하면 나머지 하나는 아무도 하지 않는다.

**방어 4개**

1. **기대수익률 앵커가 유일한 밸런스 계약이다.** 두 게임 모두 1게임분기 중앙값을 §3-4 수준
   (+5~15%)으로 맞춘다. 리스크 축이 다르므로(투자 = 고분산 · 상권 = 저분산 + 고정비) 둘 다
   살아남는다. **계수 조정의 목표 함수는 이것 하나다.**
2. **각자의 상한 장치.** 투자는 수수료(왕복 0.3%)가 회전을 억제하고, 상권은 `facility_score`
   수용 상한이 매출을 억제한다.
3. **`game_ledger` 원장 — 밸런스와 버그를 동시에 잡는 장치.**
   현금이 변한 모든 사건을 부호 있는 증감으로 남긴다. 출처는 반드시
   `initial | trade | store | settlement` 중 하나여야 한다.

   **불변식: `SUM(ledger.amount_krw WHERE user_id) == wallet.cash_krw`**

   > ⚠️ **3단계에서 원안을 고쳤다.** 원안은 `SUM == cash + 포지션 평가액 + 가게 평가액`이었는데
   > 이건 성립하지 않는다 — 평가액에는 **미실현 손익**이 들어 있고 그건 아직 일어나지 않은
   > 사건이라 원장에 대응 항목이 없다. 원장을 **현금 흐름**으로 좁히면 불변식이 등식 하나로
   > 단순해지고 검증이 정확해진다. 총자산(현금 + 포지션 평가)은 원장이 아니라 조회 시점에
   > 계산한다.

   원장 없이 지갑만 두면 어디서 돈이 새는지 영원히 모른다.
4. **붕괴 감지.** 결산 시 두 게임의 실현손익 비율을 로그로 남긴다. 90:10을 넘으면 계수 재조정
   신호다. **관측 없이 밸런싱하지 않는다.**

3. **ORM의 `user_id`에 타입을 명시했다.** `ForeignKey("users.id")`만 쓰면 game만 로드할 때
   타입이 `NullType`으로 남는다 — `users`가 auth 소유이기 때문이다. auth를 import하면
   해결되지만 그건 **스포크 직접 참조라 계약 위반**이고, 실제로 import-linter가 잡아냈다.

> **포트를 셋으로 쪼개지 않았다.** 매매 한 번이 지갑·포지션·원장 **세 테이블을 원자적으로**
> 바꾼다. 포트를 나누면 트랜잭션 경계가 유스케이스로 새어나가고, 그 순간 "지갑은 줄었는데
> 원장은 안 쓰인" 상태가 만들어질 수 있다 — 그게 바로 원장으로 잡으려던 버그다.
> `GameAccountRepository` 하나가 셋을 함께 다루고, 쓰기는 전부 커밋 한 번으로 끝난다.

## 8. 커밋 단위

- 각 커밋은 단독 배포 가능하고 **기존 엔드포인트 동작을 바꾸지 않는다.**
- **마이그레이션과 슬라이스를 한 커밋에 넣지 않는다.** admin 배포 순서 사고 선례가 있다 —
  컬럼 부재 시 전 인증 요청이 500이 났고, "신코드 재기동 **전에** alembic upgrade 먼저"가
  그때 얻은 규칙이다.
- **1단계와 5단계를 한 커밋에 넣지 않는다**(투자 게임과 상권 게임) — 이 문서 전체의 이유가 그것이다.
- 커밋 메시지는 한국어 `type(scope): 요약`.

## 12. 미해결 — 착수 전 확정할 것

- **`GAME_EPOCH_START_UTC` 실값** — 1단계 착수일에 정하고 그 뒤 불변.
- **게임 종목 12개인가 16개인가** — 화면 레이아웃(2단계)이 정해지면 확정.
- **가상 사명 목록** — 12~16개를 실재 기업과 혼동되지 않게 짓는다. 실존 상호와의 충돌을 한 번 확인한다.
- **동시 운영 가게 수 상한** — 제안: 1분기 1개, 2호점은 `facility_score ≥ 300` + 흑자 2분기.
- **`/game` 안에서 두 게임을 어떻게 나누나** — 좌우 분할 / 내부 세그먼트 탭(투자·창업) /
  단일 대시보드. 2·4단계에는 투자만 있으므로 7단계 착수 전까지 미룰 수 있다.
- **시즌 종료 알림 수단** — 푸시가 없으므로 접속 시 표시뿐인가?
- **밸런스 목표치 재확인** — §3-4의 중앙값 +5~15% / 손실 계정 35~45%가 실제 플레이 감각과 맞는지는
  9단계 실측 리포트 전까지 알 수 없다. **이 표는 가설이고, 실측이 이기면 표를 고친다.**
