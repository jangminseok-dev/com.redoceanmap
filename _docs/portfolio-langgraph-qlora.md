# 왜 LangGraph와 QLoRA를 쓰지 않았나 — 이력서·면접용 설명

> 이 문서는 프로젝트 내부를 모르는 독자(채용 담당자·면접관)를 위한 설명이다.
> 내부 기록(게이트 판정표·날짜·수치 출처)은 [[minseok/_docs/LANGGRAPH_QLORA_DEFERRAL_2026-10|LANGGRAPH_QLORA_DEFERRAL]]에 있다.

---

## 이력서에 바로 쓸 수 있는 요약

> LangGraph·QLoRA 같은 유행 기술은 "도입 게이트"(없으면 비싼 구체 작업이 있는가 · 지연 실측 ·
> 제거 계획)를 먼저 세우고 판정했다. LangGraph는 실제 사용자 질문 129건을 전수 분류해
> 다단계 추론이 필요한 질문이 0건임을 확인하고 보류했다. QLoRA는 8GB GPU에서 학습 환경을
> 구축·검증까지 마쳤지만, 기반 모델의 비상용 라이선스와 학습 데이터 부재로 투자를 멈추고
> 그 자원을 결정론 가드와 골든셋 회귀 테스트에 썼다.

---

## 1. 배경 — 이 프로젝트가 무엇인가

**RedOceanMap**은 서울 상권 공공데이터와 주식 시세를 **채팅으로 분석하는** 웹 서비스다.
2026년 5월부터 1인 개발 중이며, 다음 제약 아래서 만들었다.

| 제약 | 내용 |
|---|---|
| LLM 추론은 온프레미스 | 핵심 답변은 집 PC의 로컬 모델(Gemma 4 e4b, Ollama)이 생성한다. 외부 API(Gemini)는 일반 상식 질문과 장애 폴백에만 쓴다 |
| GPU는 RTX 3050 **8GB** 한 장 | 서빙과 학습이 같은 GPU를 써야 한다. 동시 생성은 1건이다 |
| 소형 모델이다 | 4B급 모델은 틀린다. 그래서 이 저장소의 주제는 "모델을 믿지 않고 **아키텍처로 보완**한다"다 |

이 맥락이 두 기술을 판단하는 기준이 됐다. **GPU 한 장, 생성 슬롯 하나, 1인 개발**에서는 모든
LLM 호출 하나가 사용자의 대기 시간이고, 모든 의존성 하나가 유지 비용이다.

---

## 2. 공통 원칙 — 기술 도입 게이트

이 프로젝트에서 새 라이브러리·인프라는 다음 4문항에 답해야 들어온다. 문서로 적어 두고, 패키지를
추가할 때마다 다시 통과시킨다.

| # | 문항 | 왜 묻나 |
|---|---|---|
| 1 | 이것 없이는 **과도하게 비싼 구체 작업**이 있는가? | "가독성이 좋아진다", "업계 표준이다"는 사유로 인정하지 않는다. 구체 작업을 못 대면 도입 사유가 없다 |
| 2 | 도입 범위를 **최소**로 좁혔는가? | 메타패키지·선택 의존성을 끌고 오지 않는다 |
| 3 | **지연·메모리를 실측**하고 허용선을 정했는가? | 소형 모델 서비스에서 오케스트레이션 계층의 오버헤드는 체감된다 |
| 4 | **제거 계획**이 있는가? | 포트(인터페이스) 뒤에 숨겨서 한 파일만 바꾸면 빼낼 수 있어야 한다 |

LangGraph와 QLoRA는 이 게이트를 **통과하지 못해서** 들어오지 않았다. "몰라서" 또는 "귀찮아서"가 아니다.

## 3. LangGraph — 쓸 자리에 수요가 없었다

### 3-1. LangGraph가 무엇이고 왜 고려했나

LangGraph는 LLM 호출 흐름을 **상태 머신(노드·엣지)**으로 짜는 라이브러리다. 선형 체인으로는
어려운 **순환**(근거가 부족하면 다시 검색 → 다시 생성)과 **조건 분기**를 코드로 드러내 준다.

이 서비스의 채팅은 "질문을 분류 → 15개 처리 경로 중 하나로 보냄 → 데이터 조회 → 답변 생성"
구조다. 비교·인과형 질문("A 상권과 B 상권 중 카페는 어디가 낫고 왜?")은 A 근거·B 근거·비교 축을
각각 모아야 해서, 이런 **다단계 추론 질문 전용 경로**를 LangGraph로 만드는 안을 2026년 7월에
설계까지 했다.

### 3-2. 검증 — 그런 질문을 실제로 하는가

설계 문서에 "**사용자가 실제로 그런 질문을 하는지 세어 본 뒤에** 코드를 쓴다"를 선행 조건으로
적어 두었다. 2026년 8월, 그때까지 쌓인 **실제 사용자 질문 129건을 전수 분류**했다.

| 분류 | 뜻 | 건수(대표 10문 기준) |
|---|---|---|
| vector-ok | 벡터 검색 1회로 답이 됨 | 5 |
| pg-join | SQL 조인으로 답이 됨 | 5 |
| **graph-only** | 다단계 추론·관계 탐색이 **있어야만** 답이 됨 | **0** |

착수 조건으로 정한 "graph-only ≥ 3/10"에 미달했다. **다단계 추론 경로를 만들 이유가 없었고,
그 경로를 위한 LangGraph도 이유를 잃었다.**

### 3-3. 그 외 성립하지 않았던 논거

| 일반적인 도입 논거 | 이 프로젝트의 사실 |
|---|---|
| "대화 이력을 체크포인터로 관리할 수 있다" | 이력은 이미 PostgreSQL 테이블에 있다. 체크포인터를 넣으면 이력 저장소가 **둘**이 된다 |
| "기존 체인을 노드로 감싸면 된다" | 동작하는 코드를 같은 동작의 다른 모양으로 옮기는 건 **순수 비용**이다 |
| "루프와 재시도를 깔끔하게 쓸 수 있다" | 현재 순환은 JSON 파싱 실패 시 1회 재시도가 전부다. `while` 한 줄로 충분하다 |
| "확장성을 위해 미리 깔아 둔다" | 생성 슬롯이 하나다. 노드가 늘면 질문당 LLM 호출 수가 늘고, 그게 곧 **뒤 사람의 대기 시간**이다 |

### 3-4. 대신 무엇을 했나

같은 기간에 소형 모델의 오답을 막는 쪽에 투자했다.

- **결정론 가드** — 서울 외 지역 차단, 질문 지역 보정, 직전 추천 승계, 근거 없는 입지 서술 금지를
  LLM이 아니라 코드로 막는다.
- **골든셋 회귀 테스트** — 134문항을 실제 모델로 돌려 의도 정확도·환각 숫자·금지 표현·p95 지연을
  결정론으로 채점하고 baseline 대비 게이트를 건다. LLM-as-judge는 쓰지 않는다.
- **의존성 격리** — LangChain은 `langchain-core` 1개만, 어댑터 1파일에만 import한다.
  import-linter 계약이 도메인 계층 유입을 기계적으로 차단한다.

### 3-5. 언제 다시 보나

채팅 인터랙터를 처리 경로별 핸들러로 분해한 뒤, 그 안에 **진짜 순환이 3개 이상** 생기고
실사용 질문에서 **다단계 추론 비율이 3/10을 넘으면** 게이트를 다시 판정한다.

## 4. QLoRA — 해 봤고, 멈출 이유가 셋이었다

### 4-1. QLoRA가 무엇이고 왜 고려했나

QLoRA는 LLM을 4비트로 양자화한 상태에서 작은 어댑터(LoRA)만 학습해, **소비자 GPU로도
파인튜닝을 가능하게** 하는 기법이다. 이 서비스는 의도 분류와 답변 생성을 한 모델이 맡으므로,
서비스 데이터로 파인튜닝하면 분류 정확도와 답변 형식을 끌어올릴 수 있다는 가설이 있었다.

### 4-2. 실제로 어디까지 갔나

2026년 7월, 당시 모델(EXAONE 3.5 7.8B)로 **학습 환경을 끝까지 구축하고 역전파까지 검증**했다.

| 항목 | 실측 |
|---|---|
| 설정 | NF4 4비트 + double quant + bf16, LoRA r=16(all-linear), 시퀀스 512, 배치 1 |
| 학습 파라미터 | 전체의 0.53%(42M) |
| **메모리 피크** | **7.69GiB / 8GB** |
| 부수 작업 | transformers 버전 변경에 맞춘 모델 코드 패치 2건, 임베딩 접근자 호환 패치 |

### 4-3. 멈춘 이유 세 가지

**① 라이선스.** 2026년 8월 라이선스 실사에서 EXAONE 3.5가 **비상용(NC) 라이선스**임을 확인했다.
모델·파생물·출력물까지 수익 목적 사용이 금지된다. 파인튜닝한 모델도 파생물이라 같은 제약을 받는다.
공개 서비스 전에 모델을 교체해야 하는데, **교체될 모델에 학습을 투자하는 건 매몰 비용**이었다.
실제로 2026년 9월 Gemma 4(Apache 2.0)로 교체했다.

**② GPU 예산.** 피크 7.69GiB는 배치 1 고정, 시퀀스 512 이하, 8비트 옵티마이저, gradient
checkpointing, **학습 중 서빙 모델 종료**가 모두 있어야 나오는 한계치다. 서빙과 학습이 같은 GPU를
쓰므로 학습하는 동안 **서비스가 멈춘다.** 또 한 모델이 분류와 생성을 겸하므로 분류 데이터만
학습하면 대화 능력이 깨진다. 일반 지시 데이터를 섞은 멀티태스크 학습이 필수인데, 이 예산에서는
현실성이 낮았다.

**③ 학습 데이터가 없다.** 파인튜닝은 "무엇을 가르칠 것인가"가 있어야 한다.

| 후보 데이터 | 규모 | 왜 안 되나 |
|---|---|---|
| 뉴스 감성 라벨 | 14만 건 | **같은 모델이 만든 라벨**이다. 교사의 출력을 교사에게 되먹이는 건 얻는 게 없다. 이 데이터의 정답 용도는 더 작은 분류기(KcELECTRA)로의 증류다 |
| 채팅 골든셋 | 134건 | 평가용이다. SFT 데이터로는 두 자릿수 부족하다 |
| 실사용자 질문 | 294건 | 라벨링해도 학습 규모가 안 된다 |

### 4-4. 대신 무엇을 했나

모델을 바꾸는 대신 **모델에 들어가는 입력과 나오는 출력을 통제**했다.

- 프롬프트에 원값이 아니라 **의미 해석 문장**을 넣는다(구간 폭이 보정된 피크 시간, 절대 건수를
  병기한 폐업률). 소형 모델이 숫자를 잘못 읽을 여지를 줄인다.
- 모델 교체 때는 **골든셋 게이트**로 품질 회귀를 막았다(EXAONE → Gemma 4, 임베딩 모델 교체 포함).
- 자체 모델 투자는 **작은 분류기**에 한정한다 — 유해 콘텐츠 분류기 v1은 완료, 뉴스 감성 경량 모델은
  라벨 축적 뒤 진행한다. 8GB로 충분하고 서빙을 멈추지 않는다.

### 4-5. 언제 다시 보나

실사용 질문이 **수천 건** 쌓이고 실패 사례에 "왜 틀렸는지" 라벨이 붙기 시작하면, Gemma 4 기준으로
8GB 학습 가능성과 LoRA → GGUF → Ollama 서빙 경로를 다시 검증한다.

## 5. 면접에서 받을 질문과 답

**Q. 결국 둘 다 안 썼으면 경험이 없는 것 아닌가?**
A. QLoRA는 환경 구축·역전파 검증까지 했고 메모리 피크를 실측했다. LangGraph는 설계 문서와
게이트 판정표가 있다. "써 봤다"보다 "**왜 안 쓰는지를 숫자로 설명할 수 있다**"가 1인 운영 서비스에서
더 중요한 역량이라고 판단했다.

**Q. 유행 기술을 피하는 성향인가?**
A. 아니다. LangChain(core), pgvector, Neo4j(데이터 투영까지)는 같은 게이트를 통과해서 들어왔다.
게이트가 있을 뿐이다.

**Q. 그 시간에 무엇을 얻었나?**
A. 소형 모델 환각을 코드로 막는 결정론 가드 체계, 134문항 골든셋 회귀 테스트, 아키텍처 계약 5종의
기계 검증. 모델 교체(EXAONE → Gemma 4)를 하루 안에 품질 회귀 없이 끝낼 수 있었던 건 이 투자 덕이다.

## 6. 이력서 문장 예시

- 신기술 도입에 **4문항 게이트**(구체 비용·최소 범위·지연 실측·제거 계획)를 적용. LangGraph는
  실사용 질문 129건 전수 분류로 다단계 추론 수요 0건을 확인해 보류, QLoRA는 8GB GPU 학습 환경을
  검증(피크 7.69GiB)한 뒤 기반 모델의 비상용 라이선스와 학습 데이터 부재로 투자 중단.
- 모델 파인튜닝 대신 **결정론 가드 + 골든셋 134문항 회귀 테스트**로 소형 LLM 품질을 관리.
  EXAONE → Gemma 4 모델 교체를 품질 게이트 통과 조건으로 완료.
